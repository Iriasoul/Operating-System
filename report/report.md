## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本次 Lab4 的主线是：先准备好虚拟内存映射，再建立能够独立调度的内核线程，最后通过调度器和上下文切换使线程运行。我们从本章开始解决内核如何让多个执行流使用 CPU。

对应的调用过程可概括为：`kern_init → pmm_init → vmm_init → proc_init → cpu_idle → schedule → proc_run → switch_to`。其中内存初始化为后面的进程系统提供基础；进程初始化负责创建线程；调度与切换负责把线程交给 CPU 执行。

### 3.2 功能的逐步实现

1. 模块一：虚拟内存页操作。 首先实现 `page_insert()` 和 `page_remove()`，使内核能够在已有 Sv39 页表上建立、更新和撤销映射。只有保证页表、引用计数和 TLB 的一致性，才能为后续的虚拟地址空间管理提供可靠基础。
2. 模块二：进程创建及初始化。 实现进程控制块初始化、内核栈分配、内核线程创建等，使系统具有 `idleproc`、`initproc` 等运行实体。
3. 模块三：进程调度。 通过调度器选择可运行线程，再由上下文切换函数保存和恢复寄存器现场，使新线程实际执行。

### 功能模块一：虚拟内存页操作

**负责人：** 2410966-王策

#### 模块功能描述

**修改文件：** `code/kern/mm/pmm.c`，实现位于 `//LAB4 function1 2410966` 区域。

**需要实现的函数：**

```c
int page_insert(pde_t *pgdir, struct Page *page, uintptr_t la, uint32_t perm);
void page_remove(pde_t *pgdir, uintptr_t la);
```

**功能说明：**

`page_insert()` 的功能是建立或修改线性地址 `la` 对应的物理页映射。对于新映射，目标物理页的引用计数需要增加；对于映射到同一物理页的情况，仅更新页表项；如果原来映射的是另一物理页，就减少旧页的引用计数，在旧页没有其他映射引用时释放它。成功时返回 `0`，无法分配必要的页表页时返回 `-E_NO_MEM`。

`page_remove()` 负责撤销指定线性页的映射。首先确定目标映射是否存在，再清除有效页表项、维护引用计数并使旧 TLB 翻译失效。如果目标地址本来就没有映射，则直接返回，因此同一地址允许重复删除。

两个函数依赖 `get_pte()` 查找页表项，和 `pte2page()`、`page_ref_inc()`、`page_ref_dec()`、`free_page()`、`tlb_invalidate()` 等函数。

#### 最终提示词与 spec 设计

完整内容见 [prompt.md 的提示词 1](prompt.md#提示词-1虚拟内存页操作)，报告补充时使用的源码核对要求也单独记录在该文件中。

提示词将任务拆为 `[PROMPT]`、`[RELY]`、`[GUARANTEE]`、`[SPECIFICATION]` 四部分。`PROMPT` 限定页映射维护的两个接口、修改范围和标记保留要求；`RELY` 提供真实的页描述符、Sv39 宏、分配接口及 `pte_create` 的定义，避免混淆虚拟地址、物理页号和页描述符指针；`GUARANTEE` 明确公开接口与成功、失败行为；`SPECIFICATION` 则把输入状态划分为可检查的分支。

`page_insert` 的 spec 分别覆盖无旧映射、旧映射指向同页、旧映射指向异页，以及中间页表分配失败。每种情况都同时约束最终 PTE、数据页引用计数、必要的资源回收与 TLB 同步。`page_remove` 的 spec 区分已有映射和没有映射，要求重复删除安全、删除时不新建页表。这些条件比单独要求“建立映射成功”更能检查状态是否一致。

验收将上述条件对应到具体观察量：用 `pte2page(*ptep)` 检查映射目标，用权限位检查更新结果，用 `page_ref` 检查共享与释放，用 `nr_free_pages` 检查重复映射和清理是否改变资源数量。前置条件则限定根页表、目标物理页与原引用计数有效，并针对当前普通 4 KiB 的 Sv39 页表路径；大页拆分和其他分页模式的推广在 Challenge 中单独讨论。

#### 核心实现与理解

**1. 定位 PTE，并在分配失败时恢复页表状态。**

`page_insert` 先保存 `pgdir[PDX1(la)]` 的原值，再调用 `get_pte(pgdir, la, 1)`，允许它建立缺失的中间页表。只有取得末级 PTE 后才开始修改目标数据页的引用计数，因此页表定位失败不会先增加数据页引用。

如果第一次中间表分配成功、第二次分配失败，`get_pte` 可能已经把新表挂接到根表。当前实现检查“原根表项无效，而返回后根表项有效”，取得这张本次新增的表页，恢复原根表项、使对应地址的 TLB 翻译失效，再将表页引用清零并释放，最后返回 `-E_NO_MEM`。如果原根表项已经存在，则不会错误释放原有表页。这一回滚逻辑对应当前 Sv39 的两层中间表分配流程。

**2. 根据旧映射的目标，决定数据页引用计数如何变化。**

取得 PTE 后，只有旧项包含 `PTE_V` 才通过 `pte2page` 取出旧物理页，否则将 `old_page` 视为 NULL。随后用 `old_page != page` 判断是否需要增加新页引用：

| 调用前状态 | 新页引用的处理 | 旧页引用的处理 |
| --- | --- | --- |
| 地址没有旧映射 | 增加一次 | 无旧页 |
| 地址已映射到同一物理页 | 保持不变 | 不减少、不释放 |
| 地址已映射到另一物理页 | 新页增加一次 | 更新 PTE 并同步 TLB 后，旧页减少一次；归零才释放 |

同一物理页可以同时映射到多个线性页，每新增一条由本接口管理的映射就增加一次引用。仅修改已有映射的权限时，映射数量没有增加，因此不能额外累加引用。若先删除同页映射再重新建立，还可能在旧引用为 1 时把仍要使用的页释放，所以这里直接保留同页引用并更新表项。

**3. 用物理页号重建 PTE，并在回收旧页前同步 TLB。**

新 PTE 由 `pte_create(page2ppn(page), perm)` 生成。`page2ppn` 将页描述符转换为物理页号，`pte_create` 编码页号并自动加入 `PTE_V`，其余权限由传入的 `perm` 指定；没有把内核虚拟指针直接写入页表。

无论映射目标是否变化，都会写入新的 PTE 并调用 `tlb_invalidate(pgdir, la)`。同页重映射也需要这一步，因为权限可能变化。目标替换时，执行顺序是“新页增加引用 → 写入新 PTE → TLB 失效 → 旧页减少引用并按需释放”，使旧页在被回收前不再通过该地址使用旧翻译。当前 `tlb_invalidate` 实际执行按地址的 `sfence.vma`。

**4. `page_remove()` 采用不分配页表的幂等删除。**

删除使用 `get_pte(pgdir, la, 0)`。中间页表不存在，或末级项无效时直接返回；存在映射时，先取得物理页指针，再将 PTE 清零、执行 TLB 失效，最后减少引用并在归零时释放数据页。因此一次删除不会释放仍被其他地址引用的页，重复删除也不会继续减计数或重复释放。

该函数只撤销目标映射，不自动回收中间页表。中间表可能还保存其他映射，不能仅因为删除一个地址就将它释放。框架自检在结束时另行清理测试页表，用空闲页数量验证资源恢复。


这个模块负责分配 PCB、建立内核栈、构造首次运行现场，并把新线程登记为可运行状态。执行顺序是 `proc_init → kernel_thread → do_fork → alloc_proc / setup_kstack / copy_mm / copy_thread → 登记与唤醒`。模块二完成后，调度器可以取得一个资源和现场都已准备好的线程；实际选择线程和恢复 CPU 现场由模块三完成。

#### 最终提示词与 spec 设计

完整内容见 [prompt.md](prompt.md#提示词-2进程创建及初始化)，包括初始实现提示词与根据 ASan 报错追加的命名函数修复提示词。

提示词沿用 `[PROMPT]`、`[RELY]`、`[GUARANTEE]`、`[SPECIFICATION]` 四部分模板。`PROMPT` 确定模块范围和署名；`RELY` 列出从本仓库核对过的结构体、接口、状态常量和汇编入口；`GUARANTEE` 规定返回值、资源归属以及登记顺序；`SPECIFICATION` 为六个函数分别写出前置条件、后置条件和失败行为。这样可以将自然语言中的“创建进程”落实为能检查的字段、资源和状态变化。

spec 中特别强调三项约束：新线程的 `tf` 必须属于自己的内核栈，不能指向 `kernel_thread` 的局部变量；资源准备完成后才能登记并唤醒；失败必须按资源获取的逆序清理，且不改变进程数量、PID 登记和原中断状态。验收同时覆盖正常路径与失败路径，不能只检查返回了一个正 PID。

#### 核心实现与理解

**1. `alloc_proc()`：建立安全的空白 PCB。**

先通过 `kmalloc` 获取控制块并整体清零，再设置 `state = PROC_UNINIT`、`pid = -1`、`pgdir = boot_pgdir_pa`，并分别初始化两个链表结点。这样 `runs`、`need_resched`、父进程、`mm`、中断帧、上下文、标志和名称都有确定初值。整体清零不能替代链表初始化：空链表结点需要前后指针指向自身。

**2. `proc_init()`：区分继承启动现场的 idle 与新创建的 init。**

首先初始化全局进程链表和 PID 哈希桶。`idleproc` 直接代表当前启动执行流，因此复用 `bootstack`，设 PID 为 0、状态为 `PROC_RUNNABLE`、`need_resched = 1`，命名为 `idle`，计入 `nr_process` 并设为 `current`。idle 不加入普通进程链表和正 PID 的哈希表，由调度器单独作为保底线程处理。

随后通过 `kernel_thread(init_main, "Hello world!!", 0)` 创建 init，取得 PID 后用 `find_proc` 找回并命名为 `init`。初始化结束时 `current == idleproc`、`initproc->pid == 1`、`initproc->parent == idleproc`，进程总数为 2，普通进程链表和哈希表中各有 init 一个结点。必需的 PCB 或线程创建失败时直接报告 panic，避免继续使用空指针。

**3. `kernel_thread()` 与 `copy_thread()`：构造两层首次运行现场。**

`kernel_thread` 构造清零的临时中断帧，将函数入口放入 `s0`、参数放入 `s1`，将 `epc` 指向 `kernel_thread_entry`。`status` 保留原 `sstatus` 的其他位，设置 `SPP`、`SPIE` 并清除 `SIE`，供之后的 `sret` 恢复内核执行环境。它通过 `do_fork(clone_flags | CLONE_VM, 0, &tf)` 统一进入创建流程。

`copy_thread` 在新线程栈顶预留 `sizeof(struct trapframe)` 空间，并复制模板。副本的 `a0` 设为 0；指定 `esp` 时使用传入值，否则将恢复后的 `sp` 设为新中断帧地址。之后设置 `context.ra = forkret`、`context.sp = proc->tf`。

```text
switch_to 恢复 context
    → forkret
    → forkrets(current->tf)
    → __trapret 恢复 trapframe，执行 sret
    → kernel_thread_entry
    → 调用 s0 中的函数，传入 s1 中的参数
```

这里的 `context` 服务于线程切换，`trapframe` 服务于中断返回，二者保存的信息和恢复入口不同。只有两层现场配合，第一次被调度的线程才能像从中断返回一样进入指定函数。RV64 中当前中断帧大小为 36 × 8 = 288 字节，在按页对齐的栈顶安放后仍保持 16 字节栈对齐；独立测试也检查了这一点。

**4. `do_fork()`：把资源准备与全局登记分开。**

先检查 `MAX_PROCESS`，再依次分配 PCB、设置父进程、分配独立内核栈、处理 `mm` 并复制现场。完成后才在保存中断状态的临界区中分配 PID、加入 PID 哈希表与进程链表、增加 `nr_process`，最后调用 `wakeup_proc` 将状态改为 `PROC_RUNNABLE`。临界区退出后恢复原中断状态，并返回 PID。

| 失败位置 | 返回或处理方式 | 需要释放的资源 |
| --- | --- | --- |
| 数量达到 `MAX_PROCESS` | `-E_NO_FREE_PROC` | 未分配资源 |
| PCB 分配失败 | `-E_NO_MEM` | 无 |
| 内核栈分配失败 | 返回分配错误码 | PCB |
| `copy_mm` 返回错误 | 原样返回错误码 | 先内核栈，再 PCB |

失败时尚未分配 PID 或挂接全局链表，因此不会留下可见的半初始化线程。当前 `copy_mm` 在合法前置条件下只返回 0，它的失败清理分支为后续扩展保留，本次只进行了静态检查。

**5. `copy_mm()`：保持本实验的内核线程模型。**

使用断言检查 `current->mm == NULL`，令新线程 `mm` 保持 `NULL` 并返回 0。用户虚拟地址空间与内核页表基址是两个概念：`mm == NULL` 表示没有独立用户地址空间，并不表示不能使用分页；各线程仍通过 `pgdir = boot_pgdir_pa` 共用内核映射。`clone_flags` 保留在接口中，本阶段不根据它复制用户内存。

### 功能模块三：进程调度与上下文切换

**负责人：** 2410668-吕昊远

**本模块完成日期：** 2026-11-17

#### 模块功能描述

核心实现位于 `code/kern/process/proc.c`、`code/kern/schedule/sched.c`、`code/kern/process/switch.S` 的 `LAB4 function3 2410668` 区域，提供以下接口：

```c
void cpu_idle(void);
void schedule(void);
void proc_run(struct proc_struct *proc);
void switch_to(struct context *from, struct context *to);
```

模块三完成 `cpu_idle → schedule → proc_run → switch_to` 这条执行链，让模块二创建好的线程实际使用 CPU。当前采用按进程链表循环查找的简单协作式调度，线程可以主动调用 `schedule` 让出 CPU；启动时则由 idle 的 `need_resched` 触发第一次调度。

#### 最终提示词与 spec 设计

完整内容见 [prompt.md](prompt.md#提示词-3进程调度与上下文切换)。提示词继续使用 `[PROMPT]`、`[RELY]`、`[GUARANTEE]`、`[SPECIFICATION]` 模板，并在评分测试的入口类型不匹配后追加修复提示词。

spec 将“调度”分为选择线程、切换软件状态和恢复寄存器三个层次，分别交给 `schedule`、`proc_run`、`switch_to`。前置条件说明线程链表、内核栈与初始上下文已就绪；后置条件约束 `current`、页表和实际 CPU 现场的一致性。边界要求包括空链表、全部阻塞、只有当前线程可运行、查找回绕、跳过链表头，以及进入前中断状态的恢复。

#### 核心实现与理解

**1. `cpu_idle()`：提供首次调度点。**

idle 持续检查 `current->need_resched`，需要调度时调用 `schedule`。模块二已经将 idle 的该字段设为 1，因此初始化结束后会立即寻找普通可运行线程。该函数按 `proc.h` 的约定永不返回。

**2. `schedule()`：从链表选择可运行线程。**

首先保存并关闭中断，将当前线程的 `need_resched` 清零。当前为 idle 时，从 `proc_list` 表头后开始查找；否则从当前线程的下一结点开始。遍历时跳过链表头，只选择 `PROC_RUNNABLE` 的线程；绕一圈仍未找到则使用 idle。所选线程的 `runs` 加一，与 `current` 不同时才调用 `proc_run`，最后恢复本次进入前的中断状态。

`PROC_RUNNABLE` 同时表示就绪和正在运行，因此只有当前线程可运行时，遍历可以再次选中它并继续执行，避免没有必要的现场迁移。idle 独立于普通进程链表，所以空链表或普通线程全部阻塞时仍有合法的保底目标。

**3. `proc_run()`：同步更新当前线程、页表和上下文。**

目标与当前线程相同时直接返回。否则保存并关闭中断，记录 `prev = current`，更新 `current = proc`，通过 `lsatp(proc->pgdir)` 加载目标页表并刷新 TLB，随后调用 `switch_to(&prev->context, &proc->context)`。

这里需要理解函数返回的时间：调用 `switch_to` 后，CPU 会转到另一线程；原线程以后再次被选中时，才会继续执行这个调用之后的 `local_intr_restore`。中断保存标志是该线程栈上的局部变量，所以不同线程可以恢复各自进入临界区前的状态。

`schedule` 和 `proc_run` 的中断保护可以嵌套。外层已关闭中断时，内层保存的标志为 0，恢复内层不会提前打开中断；原线程回到外层后才按外层标志恢复。新线程首次执行则由模块二构造的 `trapframe.status` 和 `sret` 完成中断状态恢复。

**4. `switch_to()`：按实际结构布局保存、恢复 14 个寄存器。**

`a0` 指向旧上下文，`a1` 指向新上下文。先通过 `STORE` 保存旧线程的 `ra`、`sp`、`s0～s11`，再从新上下文的相同偏移用 `LOAD` 恢复，最后 `ret` 跳到新 `ra`。

| 字段 | 槽位 | RV64 字节偏移 |
| --- | --- | --- |
| `ra` | 0 | 0 |
| `sp` | 1 | 8 |
| `s0～s11` | 2～13 | 16～104 |

这些寄存器共占 112 字节，与 `struct context` 一致。普通函数调用约定由调用者处理需要保留的 caller-saved 寄存器；本函数负责迁移返回位置、栈指针及 callee-saved 寄存器。两个参数指针在所有访存完成前保持有效。

新线程的 `ra` 预设为 `forkret`，因而第一次恢复后进入 `forkret → forkrets → __trapret → kernel_thread_entry`，最终调用指定线程函数。已经运行过的线程则返回到它上次调用 `switch_to` 之后继续执行。

#### 1. `local_intr_save` 与 `local_intr_restore` 如何控制中断

`local_intr_save(intr_flag)` 展开后将 `__intr_save()` 的返回值赋给 `intr_flag`。`__intr_save` 读取 `sstatus`，检查 `SSTATUS_SIE`（第 1 位，掩码为 `0x2`）；如果原先开启中断，就调用 `intr_disable()` 并返回 1，否则返回 0。`intr_disable` 通过 `clear_csr(sstatus, SSTATUS_SIE)` 清除这一位。对应地，`__intr_restore(flag)` 仅在 flag 为 1 时调用 `intr_enable()`，后者通过 `set_csr` 设置 SIE。

因此 flag 保存的是进入前的 SIE 状态，不是整个 `sstatus` 寄存器。正常遵守临界区内不自行打开中断的约定时，过程如下：

| 进入前 SIE | 保存的 flag | 临界区内 SIE | 恢复操作后的 SIE |
| --- | --- | --- | --- |
| 1 | 1 | 0 | 1 |
| 0 | 0 | 0 | 0 |

这里的“恢复”是有条件地重新开中断。flag 为 0 时，`__intr_restore` 不执行操作，不会强制再清一次 SIE；如果临界区错误地自行打开中断，单靠这次恢复不能把它重新关闭。

这种保存状态的方式允许临界区嵌套。假设外层进入前 SIE 为 1：外层保存 1 并关闭中断；内层发现已经关闭，保存 0；内层退出时不打开中断，外层退出时才恢复为 1。如果进入外层前已经关闭，则两层标志均为 0，退出后继续关闭。每层需要使用自己的保存变量，不能用同一个变量覆盖外层状态。

本实验的 `schedule → proc_run` 就采用这种嵌套关系。线程切换后，原线程以后再次运行，才从 `switch_to` 调用之后继续恢复自己的内层、外层标志。这些局部变量属于各自的内核栈，能够随线程保留。

SIE 控制当前 hart 在 S 模式下的中断接收，实际响应还依赖相应中断源的使能等条件；它不会屏蔽同步异常，也不能阻止其他 hart 访问共享数据。与此不同，SPIE 用于记录陷入前的中断状态，`sret` 根据 SPIE 恢复 SIE；本题的两个宏直接操作 SIE，并未完整保存或恢复 SPP、SPIE 等字段。上述硬件语义核对了 [RISC-V 官方 Supervisor ISA 的 `sstatus` 说明](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html)。

#### 2. 不同分页模式与 `get_pte()` 中两段相似代码的原因

三种分页模式都把虚拟地址拆成多级索引和页内偏移，硬件逐级读取页表。基本参数如下；地址位宽指有效虚拟地址位数，Sv39/Sv48 的地址仍保存在 64 位寄存器中。参数参照 [RISC-V 官方 Supervisor ISA 的 Sv32、Sv39、Sv48 章节](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html)。

| 比较项 | Sv32 | Sv39 | Sv48 |
| --- | --- | --- | --- |
| SXLEN | 32 | 64 | 64 |
| 有效虚拟地址位数 | 32 | 39 | 48 |
| 4 KiB 页的地址拆分 | 10 + 10 + 12 | 9 + 9 + 9 + 12 | 9 + 9 + 9 + 9 + 12 |
| 页表级数 | 2 | 3 | 4 |
| PTE 大小 | 4 字节 | 8 字节 | 8 字节 |
| 每张 4 KiB 页表的表项数 | 1024 | 512 | 512 |
| `satp.MODE` 编码 | 1 | 8 | 9 |

由地址位数可算出可表示的地址空间总量分别为 4 GiB、512 GiB 和 256 TiB。Sv39 要求地址的 63～39 位等于第 38 位，Sv48 要求 63～48 位等于第 47 位，因此它们在 64 位地址中形成低、高两段规范地址范围，不能把中间空洞视为可用空间。更多级数可以覆盖更大的范围，也会增加未命中 TLB 时的最深遍历层数和部分页表内存开销。

本仓库实际使用 Sv39：`PDX1SHIFT = 30`、`PDX0SHIFT = 21`、`PTXSHIFT = 12`，三个索引均取 9 位，即掩码 `0x1FF`；RV64 的 `pte_t` 为 8 字节。`mmu.h` 文件顶部仍有 Sv32 的旧示意注释，判断当前实现应以这些实际宏、类型以及 `satp` 的模式设置为准。

`get_pte()` 的第一段通过 `PDX1(la)` 选中根表项：若对应的下一级页表不存在，且 `create` 允许，就分配一页、设置该页引用计数、清零页表，再把物理页号写入根表项。第二段通过 `PDX0(la)` 选中下一层表项，按同样步骤查找或创建末级页表。最后通过 `PTX(la)` 返回末级 PTE 的地址。

两段代码相似，是因为它们执行相同的“索引当前层 → 检查下一层是否存在 → 按需创建 → 进入下一层”操作，区别仅在所处层级与使用的索引。它们分配的是页表页，目标数据页由 `page_insert` 的调用者提供；清零可保证新表项初始无效，页表页的引用计数也与数据页的映射引用计数分开维护。

在根表已准备好、一直向下建立 4 KiB 映射的前提下，Sv32 通常只需一次这样的中间页表创建步骤，Sv39 需要两次，Sv48 需要三次。推广到其他模式还必须同步调整表项宽度、索引位数、层数和地址合法性检查，不能仅复制或删掉一段代码。

还要区分大页与下一级页表：有效项中的 R 或 X 可表示叶子映射；非叶子指针项的 R/W/X 均为 0，W 为 1 而 R 为 0 的组合属于无效编码。叶子可以出现在较高层，且大页需要相应对齐。当前 `get_pte` 按固定三级向下寻找末级 PTE，只检查 V，未实现通用的大页识别；启动页表却含有 1 GiB 叶子。因此本函数主要用于当前实验的普通 4 KiB 映射路径，不能直接把已有的大页叶子当成下一级页表继续遍历。这一边界也是设计通用 walker 时必须补充的内容。

#### 3. 是否应该拆分页表项查找与页表页分配

当前 `get_pte(pgdir, la, create)` 将查找与可选分配合在一起，优点是调用简洁、只遍历一次，各层的索引和地址转换代码可以复用。对于固定 Sv39、规模较小的 Lab4，这种接口能够完成任务：`page_insert` 使用 `create = 1`，`get_page` 和 `page_remove` 使用 `create = 0`，后者不会因查询或删除不存在的映射而分配新页表。

其不足在于同一函数有两种不同的副作用，调用者需要额外理解 create 参数、内存不足的失败行为，以及清理职责。尤其要分清：返回非空指针仅表示末级 PTE 所在的页表已存在，并不保证该 PTE 的 V 位为 1；查询映射时仍需检查表项是否有效。返回 NULL 也不能一概理解为“目标数据页未映射”，它可能表示中间页表不存在，或创建中间表时分配失败。

本仓库有一个具体例子：若第一次分配中间页表成功、第二次分配失败，`get_pte` 会返回 NULL，但第一张新表可能已经挂接到根表。当前 `page_insert` 记录原根表项，并在这条失败路径恢复根表项、释放本次新建的中间表。这满足当前两段分配流程的需要，但回滚责任依赖调用者了解函数内部，直接调用 `get_pte(..., 1)` 的其他路径不能据此假设失败时完全没有修改页表。

我倾向于在扩展为通用虚拟内存子系统时，拆分对外接口并保留共享的内部遍历实现，例如：

| 建议接口 | 职责与契约 |
| --- | --- |
| `lookup_pte(pgdir, la)` | 只定位已有末级表项，不分配；中间表缺失时返回 NULL，返回 PTE 后仍需判断有效位 |
| `ensure_pte(pgdir, la, &ptep)` | 按需建立中间表，成功输出 PTE 指针，失败返回明确错误并撤销本次新增的表页 |
| 内部 walker | 共享各层索引、合法性检查和叶子识别，必要时返回 PTE 所在层级，避免维护两套遍历算法 |

`ensure_pte` 可以记录本次新分配的表页与挂接位置，失败时按逆序解除挂接并回收；已有表页和已有映射保持不变。面向大页时还需明确返回较高层叶子、拒绝不支持的操作，或先拆分大页后再建立细粒度映射。并发修改时的锁保护以及页表变化后的 TLB 同步，也必须写入接口契约；仅把函数改成两个名字不会自动解决这些问题。

因此本实验保留现有接口即可，作为思考题给出上述改进设计。面向多种分页模式、大页和更复杂的失败处理时，分离查询与分配的外部语义更利于理解、测试和维护。本次 Challenge 未修改运行代码；对照源码和官方规范完成静态核对，已有 30/30 仍是编程模块的实际评分。

## 六、实验总结与收获

### 对操作系统的理解

**1. 本阶段重要知识点及其与操作系统原理的联系**

模块一补充：

| 实验知识点 | 对应 OS 原理 | 联系与当前实现的边界 |
| --- | --- | --- |
| Sv39 多级页表与 PTE | 虚拟地址到物理地址的转换 | 通过索引定位末级表项，将物理页号与权限写入 PTE；当前接口主要服务普通 4 KiB 映射 |
| 同页多地址映射与引用计数 | 共享内存和资源生命周期 | 多条映射可引用同一物理页；撤销一条只减少一次引用，最后一条撤销后才允许回收 |
| PTE 权限更新 | 页级访问保护 | 表项描述读、写、执行等访问条件；当前实验检查权限位并验证内核访问，尚未形成完整用户进程隔离 |
| 页表修改与 TLB 失效 | 地址翻译缓存的一致性 | 内存中的 PTE 变化需要同步已有翻译，回收旧页前应撤销该地址对旧页的访问路径 |
| 中间表分配失败回滚 | 内核资源管理与错误恢复 | 创建映射可能同时取得多项资源，失败时要恢复原页表并只回收本次新增资源 |

模块二补充：

| 实验知识点 | 对应 OS 原理 | 联系与当前实现的边界 |
| --- | --- | --- |
| PCB 与进程状态 | 进程描述、生命周期 | 用控制块记录资源和执行状态；本阶段 `PROC_RUNNABLE` 同时涵盖就绪与正在运行，未单设 RUNNING 状态 |
| 独立栈与共享页表 | 线程的资源共享模型 | 内核线程共享地址映射，但各有内核栈和寄存器现场，因而能够分别保存执行进度 |
| `context` 与 `trapframe` | 上下文切换与中断现场恢复 | 分别服务于函数级切换和中断返回；新线程预先构造两层现场，复用既有恢复入口 |
| PID、链表与哈希 | 进程标识及组织管理 | PID 标识线程，链表支持遍历，哈希表支持查找；三者必须与进程数量和状态保持一致 |
| 临界区与失败清理 | 并发互斥及资源管理 | 在单核模型中关中断保护登记，按逆序回收失败资源；关本核中断本身不能提供多核互斥 |

模块三补充：

| 实验知识点 | 对应 OS 原理 | 联系与当前实现的边界 |
| --- | --- | --- |
| 按链表循环选择 runnable 线程 | CPU 调度、轮转与调度点 | 当前通过显式调用 `schedule` 协作让出 CPU，尚未按时间片抢占 |
| `current`、页表与寄存器一起切换 | 进程执行现场的一致性 | 三者需在临界区内同步改变，避免执行现场与当前线程身份不一致 |
| 嵌套保存中断状态 | 临界区与中断控制 | 内层恢复不会提前打开外层关闭的中断；原线程再次运行后恢复自己的保存标志 |
| `satp` 与 `sfence.vma` | 地址空间切换与 TLB 一致性 | 根页表物理地址要编码为 Sv39 的根物理页号，更新后同步 TLB；当前线程实际共用内核页表 |
| `ra/sp/s0～s11` 保存恢复 | ABI 与上下文切换 | 利用函数调用约定保存所需现场，新线程与已运行线程通过不同的预设返回位置继续执行 |

**2. OS 原理中重要、但本实验尚未实现或未覆盖的内容**

本实验没有实现独立用户地址空间、用户态进程加载、系统调用、写时复制、按需缺页、页面置换，也没有完整的退出、等待和僵尸进程回收。当前 `do_exit` 仍沿用框架的 panic 行为。模块三已使内核线程实际获得 CPU 并协作轮流运行，时间片抢占、优先级、多核调度和多核互斥仍属于后续扩展。

### AI 协作开发的经验

模块二的实践表明，提示词需要同时写清“有哪些字段和接口”与“完成后应满足什么状态”。如果只要求创建线程，很容易遗漏栈内中断帧的归属、子线程返回值、失败回收或唤醒顺序。将这些要求写成可执行断言后，可以用分配失败注入与资源计数检查返回值之外的行为。

验证也应区分层次：交叉编译能检查实际目标平台的类型和语法，带内存检查的独立测试能暴露命名函数的越界读取及创建逻辑问题，而 QEMU 联调才能进一步确认启动、页表和真实寄存器恢复。记录实际运行的命令、错误与修复，比将预期输出当作验证结果更能说明 AI 生成代码是否满足 spec。

模块三联调还说明，遇到评分失败时要先定位失败层次。本次第一次失败发生在测试源码编译，根因是辅助函数返回类型与入口接口不一致；保持评分断言不变、修正类型后，再用实际 30/30 和多线程运行结果验证核心实现。评分日志与独立测试共同保存了这一过程。
