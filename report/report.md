## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本章围绕中断与异常处理展开，核心是让内核能够响应执行过程中发生的事件，并在处理结束后正确恢复执行。与 Lab2 主要管理内存资源不同，本实验关注执行状态的保护与控制转移：时钟事件可能在任意时刻打断内核，断点或非法指令也可能使当前执行暂时停止，系统需要在处理这些事件的同时，保证原有寄存器和返回位置符合预期。

实现这一目标的基础是统一的 Trap 机制。硬件在事件发生时记录原因、返回地址和相关状态，软件进一步保存通用寄存器，形成完整的 Trap frame。处理函数据此判断事件类型并执行相应操作，随后由恢复代码还原现场，通过异常返回指令继续运行。因此，上下文保存与恢复保证处理过程不会意外破坏原有执行状态，原因分类和处理策略则决定系统如何响应具体事件。

中断与异常虽然共用入口，返回语义却有所不同。时钟中断属于异步事件，处理后应保留原返回位置，并重新设置下一次时钟事件，以支持持续计数和周期输出；断点与非法指令属于同步异常，本实验在输出诊断信息后，按指令长度调整返回地址，避免重复执行同一条故障指令。由此，本章将现场保护、事件处理和正确返回联系起来，为后续进程调度、系统调用及更完整的故障处理建立基础。

### 3.2 功能的逐步实现

| 顺序 | 功能 | 依赖关系与目的 |
|------|------|----------------|
| 1 | 确定 Trap frame 布局，完成入口与恢复 | 建立可靠的现场保存、传参与返回机制，是所有处理函数的基础 |
| 2 | 恢复内存初始化，保证启动映射有效 | 为正式内核提供可运行的内存与地址环境 |
| 3 | 实现中断分类和持续时钟 | 在可正确返回的基础上处理重复异步事件 |
| 4 | 实现异常分类与 EPC 更新，完成整体验证 | 按同步异常语义选择返回位置，检查各模块能否协同运行 |

本实验复用 Lab2 的物理内存管理基础，重点转向执行状态的保存与恢复。当前默认页管理器为 First-Fit；Buddy、SLUB 等扩展不属于本次实现范围。

## 四、实验内容与实现

### 功能模块一：Trap 上下文恢复与 Trap 入口

**负责人：** 2412449-石晨昊

#### 模块功能描述

本模块在既有 `SAVE_ALL` 的基础上完成 Trap 返回路径，并把汇编入口与 C 语言处理函数连接起来。Trap 发生时，硬件记录原因、返回地址和状态，`SAVE_ALL` 再将通用寄存器保存为 Trap frame；本模块负责将该帧传给 `trap()`，在处理函数返回后恢复保存状态，最后由 `sret` 回到原执行位置。其正确性取决于保存布局、RISC-V 调用约定和特权返回语义的一致。

**需要实现/修改的函数：**

```asm
RESTORE_ALL
__alltraps
```

相关 C 接口为：

```c
void trap(struct trapframe *tf);
```

**功能说明：**

RV64 下 `REGBYTES=8`，Trap frame 由 36 个字宽组成，共 288 字节。槽位 0～31 对应 x0～x31，槽位 32～35 依次保存 `sstatus`、`sepc`、`sbadaddr/stval` 和 `scause`。`RESTORE_ALL` 先用临时寄存器恢复 `sstatus`、`sepc`，再恢复通用寄存器，最后从槽位 2 恢复 Trap 前的 `sp`。在恢复过程中保持当前 `sp` 作为帧基址，能够避免提前改动栈指针导致后续加载访问错误。

`__alltraps` 在 `SAVE_ALL` 后执行 `mv a0, sp; jal trap`，按调用约定把当前 Trap frame 作为第一个参数传递给 C 函数。`trap()` 返回后进入已有的 `__trapret`，由 `RESTORE_ALL` 和 `sret` 完成恢复。处理函数对帧中 `epc`、寄存器或 `sp` 的合法修改会在返回时生效，而 `badvaddr` 和 `cause` 只用于诊断，不在恢复宏中写回 CSR。

### 功能模块二：中断与异常处理

**负责人：** 2410966-王策；2410668-吕昊远

#### 模块功能描述

本模块由统一的 `trap_dispatch()` 分发中断和异常。中断处理使用 `scause` 的最高位区分中断标志，再按原因分类；Supervisor 时钟中断需要重新设置下一事件、累计 `ticks`、周期输出并在项目约定的次数后关机，其他已知中断只输出类别，未知中断输出原因和完整 Trap frame。异常处理针对非法指令和断点输出原始 EPC，并依据指令编码判断 16 位或 32 位长度后更新保存的 EPC；其他异常只作诊断输出。

**需要实现/修改的函数：**

```c
void interrupt_handler(struct trapframe *tf);
void exception_handler(struct trapframe *tf);
```

内部辅助函数为：

```c
static inline uintptr_t interrupt_reason(uintptr_t cause);
static size_t instruction_length(uintptr_t epc);
static void advance_epc(struct trapframe *tf, size_t len);
```

**功能说明：**

`interrupt_handler()` 去除 cause 的最高位后进行分类，同时保留帧中的原始 cause。对 `IRQ_S_TIMER`，每次调用 `clock_set_next_event()`，使下一次中断能够继续产生；随后将 `ticks` 加一，每 100 次调用已有的 `print_ticks()`。本项目将十次统计输出后的 `sbi_shutdown()` 作为运行结束策略，该数值是项目配置，不是实验框架额外规定。其他已知中断不修改 EPC 或时钟计数，未知原因以完整的 RV64 十进制编号输出并调用 `print_trapframe()`。

`exception_handler()` 对 cause 2 和 cause 3 分别处理非法指令和断点。它先输出异常发生时的 EPC，再读取 EPC 处的低 16 位编码：低两位不全为 1 时按 2 字节处理；低两位为 1 且低五位不全为 1 时按 4 字节处理；更长编码不在本实验支持范围内，只打印帧而不猜测长度。这样既能处理压缩断点，也能处理位于 2 mod 4 地址的 32 位指令，避免因统一加 2 或加 4 而重复执行或跳过后续指令。

## 六、实验总结与收获

### 6.1 实验知识点与 OS 原理的联系

| 实验知识点 | 对应 OS 原理 | 含义、关系与差异 |
|------------|-------------|------------------|
| Trap frame 与恢复顺序 | 执行上下文保护 | 保存被打断程序状态；帧也是恢复时的寻址依据，因此 `sp` 最后恢复 |
| 硬件 CSR 与软件寄存器保存 | 中断处理中的软硬件分工 | 硬件提供原因和返回状态，软件补齐通用寄存器，二者共同保证透明返回 |
| 汇编调用 C 与 `sret` | ABI、异常返回和特权控制 | ABI 解决函数调用接口，`sret` 解决 Trap 返回，两者不能相互替代 |
| 原因分类与 EPC 更新 | 异步中断和同步异常 | 时钟返回保留 EPC；断点和非法指令按本实验策略跳过故障指令 |
| 时钟重设与计数 | 时钟管理和抢占基础 | 周期事件提供调度时机，本实验尚未实现任务调度或进程切换 |
| 本地中断使能保存恢复 | 临界区保护 | 防止本 hart 中断重入，不能代替多核锁和内存顺序控制 |
| 启动恒等映射与高地址映射 | 虚拟内存与引导 | 地址翻译开启后必须覆盖过渡执行路径，页表映射与物理内存分配是不同层次 |

本实验加深了对“处理事件时不破坏原执行状态”的理解。Trap frame 是一次陷入的现场记录；完整进程切换还需要进程状态、地址空间和调度策略，不能与 Trap 返回等同。

### 6.2 AI 协作开发的经验

**以接口和不变量表达规格。** 提供真实布局、原因宏和 ABI，比笼统要求“实现中断处理”更有效；返回后哪些字段可变、哪些必须保持，应在 Spec 中明确。

**人工核对体系结构语义。** AI 生成代码仍需检查数据宽度、指令长度和恢复顺序。完整的 64 位接口不应因常见测试只使用小编号而被简化。

**按验证范围评价结果。** 编译、独立模块检查、正常启动和官方评分分别说明不同层次的正确性。测试通过应结合环境和覆盖范围解释，不能替代对实现原理的理解。

### 6.3 OS 原理中重要但本实验未对应实现的内容

| 原理内容 | 本实验尚未实现的部分 |
|----------|----------------------|
| 进程与调度 | 任务队列、时间片分配、进程切换和调度策略 |
| 用户态隔离与系统调用 | 用户地址空间、Trap 栈切换、系统调用表与参数检查 |
| 缺页恢复与虚拟内存管理 | 按需分页、页替换、交换和写时复制 |
| 多核同步 | 共享状态的锁、原子操作和内存一致性控制 |
| 外设与中断控制器 | PLIC 领取/完成、设备状态清除和中断下半部 |
| 故障隔离与持久化 I/O | 故障任务处理、文件系统、块缓存和恢复机制 |

本次实验主要建立了 Trap 处理的基础路径，但是对于完整的 OS 还要在此基础上继续完善，例如连接调度、地址空间和设备管理等问题，还并未进行对应的实现。
