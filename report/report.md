## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本实验在能够启动、管理内存的内核基础上增加 Trap 处理。Trap 包括中断与异常：硬件负责记录返回地址、原因与部分状态并转入入口，软件还需要保存通用寄存器、执行处理逻辑，最后恢复执行环境。

从代码阅读角度，可沿“上下文保存与恢复 → 汇编入口与 C 接口 → 中断与异常处理”理解各部分；一次实际 Trap 的执行顺序如下：

```mermaid
flowchart TD
    A[发生 Trap，硬件更新相关 CSR] --> B[通过 stvec 进入 __alltraps]
    B --> C[SAVE_ALL 在内核栈上保存 Trap frame]
    C --> D[a0 传入帧地址，调用 trap]
    D --> E[trap_dispatch 分发中断或异常]
    E --> F[C 处理函数返回]
    F --> G[__trapret 执行 RESTORE_ALL]
    G --> H[sret 根据恢复后的状态返回]
```

模块一负责其中“把帧交给 C”与“从帧恢复状态”两个连接点，模块二负责原因分类和具体行为。`SAVE_ALL` 已由框架给出。硬件只自动更新 Trap 相关 CSR，不会替软件保存全部通用寄存器；普通 C 调用约定也不能替代完整的 Trap 上下文保存。

系统启动时先完成 BSS 清零、DTB 解析和内存初始化，再设置时钟事件并开启中断。当前 `kern_init()` 在 `pmm_init()` 前后各调用一次 `idt_init()`，将 `stvec` 指向 `__alltraps`、将 `sscratch` 置零；随后 `clock_init()` 开启 `sie.STIE` 并设置首个事件，`intr_enable()` 设置 `sstatus.SIE`。接收 Supervisor 时钟中断需要局部使能、全局使能和事件条件共同满足。

## 四、实验内容与实现

### 4.1 功能模块一：Trap 上下文恢复与 Trap 入口

**负责人：2412449-石晨昊。**

正式实现位于 [trapentry.S](../code/kern/trap/trapentry.S)，结构体布局位于 [trap.h](../code/kern/trap/trap.h)。模块一实现阶段只填写两处 `lab3 function1` 标记，并将 `YOUR CODE` 替换为学号 `2412449`；未修改 `SAVE_ALL`、结构体或其他成员负责的处理函数。

#### 模块功能描述

`SAVE_ALL` 将当前处理器上下文组织成内存中的 `struct trapframe`。`__alltraps` 把这个结构体的地址传给 `trap()`，使 C 代码可以查看 Trap 原因和返回状态。`trap()` 返回后，`RESTORE_ALL` 读取同一个帧，恢复处理器执行所需的寄存器；已有的 `sret` 完成返回。

恢复使用的是处理完成后的帧内容。因此，如果处理函数合法调整了 `tf->epc` 或其他保存值，这些调整应在返回时生效。

#### Trap frame 与寄存器布局

当前 RV64 框架中 `REGBYTES=8`，共保存 36 个寄存器宽度的字段，大小为 288 字节。

| 槽位 | RV64 字节偏移 | 内容 | 恢复处理 |
|------|----------------|------|----------|
| 0 | 0 | `x0` | 保持硬连线零值，无需加载 |
| 1 | 8 | `x1/ra` | 从对应槽位恢复 |
| 2 | 16 | Trap 发生前的 `x2/sp` | 最后恢复 |
| 3～31 | 24～248 | `x3～x31` | 按编号恢复 |
| 32 | 256 | `sstatus` | 写回对应 CSR |
| 33 | 264 | `sepc` | 写回对应 CSR |
| 34 | 272 | `sbadaddr/stval` | 已保存的诊断信息，本模块不写回 |
| 35 | 280 | `scause` | 已保存的原因信息，本模块不写回 |

`SAVE_ALL` 先把旧 `sp` 写入 `sscratch`，再下移栈指针建立帧。随后通过 `csrrw s0, sscratch, x0` 取出旧 `sp`，保存到槽位 2，并清零 `sscratch`。这说明当前帧基址与原始栈指针不是同一个值。

#### RESTORE_ALL 的实现

首先借用 `s0`、`s1`，读取帧中的返回状态并写回 CSR：

```asm
LOAD s0, 32*REGBYTES(sp)
LOAD s1, 33*REGBYTES(sp)
csrw sstatus, s0
csrw sepc, s1
```

此时借用 `s0`、`s1` 是安全的，因为它们原本的值已经保存在帧中。随后按槽位恢复 `x1`、`x3～x31`，其中也包括 `x8/s0` 和 `x9/s1`，避免把临时使用的值带回被打断程序。

最后执行：

```asm
LOAD x2, 2*REGBYTES(sp)
```

所有帧读取都依赖当前 `sp`。如果提前恢复 `sp`，后续加载就会以错误地址为基址。因此必须最后恢复。直接读取保存槽位也支持处理函数合法修改帧中的栈指针；仅给当前栈指针加 288 无法体现这种修改。

本宏不对 `epc` 固定加 2 或加 4，也不强制改变 `SPP`。异常是否跳过指令由异常处理层决定；返回目标和状态应来自处理后的帧。

#### __alltraps 的实现与调用约定

在已有 `SAVE_ALL` 之后补入：

```asm
mv a0, sp
jal trap
```

`a0` 是第一个整数或指针参数寄存器，因此 `trap()` 收到的 `tf` 就是当前帧地址。`jal` 将调用返回地址写入 `ra`；旧 `ra` 与旧 `a0` 已在帧中保存，最终由恢复宏还原。C 函数返回后，执行流自然进入已有的 `__trapret`。

RV64 标准调用约定要求函数入口栈按 16 字节对齐。输入内核栈对齐时，分配 288 字节仍保持对齐，因为 288 是 16 的整数倍。本模块没有额外调整栈指针。调用约定依据见 [RISC-V psABI](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_integer_calling_convention)。

#### sret 与普通函数返回的区别

`jal trap` 和 C 函数返回解决“汇编与 C 之间如何调用”的问题。`sret` 则依据 `sepc` 返回，并按 `sstatus` 中保存的字段处理特权级与中断使能状态。当前实验的 Trap 来自内核态，不能把“执行 `sret`”一概描述为“切换到用户态”。相关机制见 [RISC-V 特权架构规范](https://docs.riscv.org/reference/isa/v20240411/_attachments/riscv-privileged.pdf)。

### 4.2 功能模块二：中断分类与持续时钟

**分工负责人：2410966-王策。** 实现位于 [trap.c](../code/kern/trap/trap.c)，依赖 [clock.c](../code/kern/driver/clock.c)、[sbi.h](../code/libs/sbi.h) 和已有的 Trap 分发逻辑。

#### 中断原因与保存状态

`trap_dispatch()` 将 `tf->cause` 转为 `intptr_t` 后检查符号：最高位为 1 时转入 `interrupt_handler()`，否则转入 `exception_handler()`。在 RV64 下，bit63 是中断标志，其余位才是原因编号。处理函数收到的仍是原始 `cause`，因此使用局部值提取编号：

```c
return cause & ~((uintptr_t)1 << (sizeof(uintptr_t) * 8 - 1));
```

这一操作既支持真实入口传入带标志的值，也支持官方测试直接传入裸编号；没有把去掉标志后的值写回 `tf->cause`。中断处理不调整 `tf->epc`，因为时钟事件与某条故障指令无关，返回后应从硬件记录的位置继续执行。

当前框架定义 U/S/H/M 的软件、时钟和外部中断编号。除 Supervisor 时钟外，其余已知编号只输出对应类别，不增加 `ticks`、不设置本实验的时钟事件、不触发统计关机。这里的 H 类名称沿用框架宏，不表示本实验实现了虚拟化中断控制或真实外设驱动。未知编号先输出完整十进制原因，再调用现有 `print_trapframe(tf)`。

#### 时钟事件、周期输出与关机

`clock_init()` 通过 `clock_set_next_event()` 安排首次时钟事件，并将 `ticks` 清零。后续每次 `IRQ_S_TIMER` 都必须重新设置事件，否则只有初次定时器到期，不能形成持续中断。当前处理顺序是：

```c
clock_set_next_event();
ticks ++;
if (ticks % TICK_NUM == 0) {
    print_ticks();
    tick_reports ++;
    if (tick_reports >= SHUTDOWN_AFTER) {
        sbi_shutdown();
    }
}
```

`TICK_NUM=100` 控制输出间隔；`tick_reports` 单独记录累计输出次数，不通过清零 `ticks` 实现周期输出。`SHUTDOWN_AFTER=10` 是本项目明确采用的暂定策略，单位是“统计输出次数”，不是教师给定的数值。因此正常启动时，第 100、200……1000 次时钟中断各输出一行 `100 ticks`，第十行输出完成后才请求关机。每行文本表示本次统计间隔为 100 次，不表示计数器一直等于 100。

驱动使用 `rdtime` 读取时间，并通过 SBI 设置 `当前时间+100000` 的下一事件。现有正常启动日志中的定时器频率为 10 MHz，对应名义间隔约 10 ms、每秒约 100 次中断。处理开销和虚拟机调度会影响实际时间，本次验证不把它当成精确计时基准，也没有实现补偿漏拍的周期调度器。

保留原有 `print_ticks()` 和 `DEBUG_GRADE` 分支：若主动开启该宏，函数会输出测试结束文本并 panic；本次正常启动和 Lab3 官方评分未额外启用它，其行为应与正常自动关机区分。

### 4.3 功能模块二：异常分类与返回地址更新

**分工负责人：2410668-吕昊远。** 主要实现为 `exception_handler()`，内部辅助函数为 `instruction_length()` 和 `advance_epc()`。

#### 模块功能与地址含义

非法指令（cause=2）和断点（cause=3）先输出原始 `tf->epc`，再更新保存的返回地址。正式内核使用高地址虚拟地址，不能把 EPC 截断为 32 位，也不能再次转换成物理地址。当前输出分别为：

```c
cprintf("Illegal instruction at 0x%016lx\n", tf->epc);
cprintf("Breakpoint at 0x%016lx\n", tf->epc);
```

`RESTORE_ALL` 随后把修改后的 `tf->epc` 写回 `sepc`，`sret` 才会从下一条指令继续。如果只输出文本而不推进 EPC，就会重新执行同一条故障指令并反复进入异常。

本实验对非法指令采取“诊断后跳过”的教学策略，不实现指令模拟或进程终止。其他未要求恢复的异常仅打印帧，EPC 保持不变；若它们真实发生且故障条件仍存在，返回后可能再次异常，不能把兜底输出写成通用恢复能力。

#### 根据编码判断 16/32 位长度

RISC-V 支持压缩指令，同样的断点助记符可能被汇编器编码为 16 位 `c.ebreak` 或 32 位 `ebreak`。当前方法只读取指令起始处的低 16 位：

| 低位条件 | 本轮解释 | 行为 |
|----------|----------|------|
| `low[1:0] != 0b11` | 16 位编码长度 | EPC 加 2 |
| `low[1:0] == 0b11` 且 `low[4:2] != 0b111` | 32 位编码长度 | EPC 加 4 |
| 低五位均为 1 | 本轮不解码的更长编码前缀 | 打印帧，EPC 不变 |

这里识别的是编码长度，不是证明该指令合法。`0x0000` 是两字节的非法编码，仍应按两字节跳过；官方非法指令用例 `.word 0x0000007b` 是四字节。只读取 `uint16_t` 也避免了在地址模 4 等于 2 时依赖未对齐四字节访问。

读取前提是 EPC 指向可读取、至少两字节对齐的内核指令地址。本次没有用户地址安全取指、跨不可访问页面取指或无法访问指令地址时的恢复机制；`badvaddr` 也没有被一概当成指令内容使用。

#### Spec 与提示词设计

异常部分与中断部分共用提示词 3，但分别规定前后置条件。前置条件强调可读取内核指令地址和本轮支持的长度；后置条件仅允许更新已支持异常的 EPC，禁止意外改写通用寄存器、status、cause 或 badvaddr。

| 情况 | 后置条件 | 验收方式 |
|------|----------|----------|
| 16 位断点/非法指令 | 输出原始地址，EPC 精确加 2，其余帧字段不变 | 直接调用加真实指令触发 |
| 32 位断点/非法指令 | 输出原始地址，EPC 精确加 4；支持地址为 2 mod 4 | 显式编码、反汇编检查、返回后哨兵比较 |
| 更长编码前缀 | 输出诊断和帧，EPC 不变 | 构造低 16 位为 `0x001f` 的直接调用 |
| 其他异常 | 只打印帧，不读取 EPC 指向内存，整帧不变 | cause=20，使用不可读地址哨兵 |

规格没有要求所有异常统一加 4，也没有把所有断点统一视为 2 字节。模块一负责落实保存帧，模块二负责决定是否以及如何改变返回位置，两者通过同一个 Trap frame 协作。

### 4.5 启动映射修复与 QEMU 参数适配

#### 分页开启后的取指为何仍需要恒等映射

正式启动代码写入 `satp` 时，PC 仍位于物理装载附近。最早故障发生在 `0x80200038` 的 `sfence.vma` 取指，原因 `0xc` 为指令缺页。它对应 Sv39 根索引 2：

```text
VPN[2] = (0x80200038 >> 30) & 0x1ff = 2
```

修复前只有根索引 511 有效，低地址没有映射，因此尚未执行跳往高地址的指令就先取指失败。故障日志中后来反复出现的 `0x80200000` 属于后续现象，不能据此替代第一次故障的位置。先前隔离副本上的诊断也不能作为正式源码已经修复的证据，正式修复后才重新执行正常启动和评分。

本次在 [entry.S](../code/kern/init/entry.S) 保留高地址项，新增低地址恒等项：

```asm
.zero 8 * 2
.quad (0x80000 << 10) | 0xcf
.zero 8 * 508
.quad (0x80000 << 10) | 0xcf
```

| 根索引 | 虚拟范围 | 对应物理范围 | PTE |
|--------|----------|--------------|-----|
| 2 | `[0x80000000,0xc0000000)` | `[0x80000000,0xc0000000)` | `0x200000cf` |
| 511 | `[0xffffffffc0000000,2^64)` | `[0x80000000,0xc0000000)` | `0x200000cf` |

两项都是 1 GiB 叶项，PPN 为 `0x80000`，V/R/W/X/A/D 置位，U/G 清零；权限沿用教学框架。根表项数为 `2+1+508+1=512`，占 4096 字节，没有挤占随后保存 hartid 和 DTB 的位置。静态检查见 [页表检查日志](validation/boot/logs/page_table_check.log)。窗口上界 `2^64` 只作为数学排他边界，不在普通 `uint64_t` 变量中表示。

该修复保证从开启分页到跳入高地址 `kern_init()` 的过渡取指可达。页表覆盖 1 GiB 窗口不意味着这 1 GiB 都存在或可分配，实际可分配范围仍由 DTB 和 `page_init()` 决定。本轮没有改变原有精确栈顶设置、hartid/DTB 保存或高地址跳转逻辑。

#### 版本差异与验证入口

QEMU 7.0 环境中的另一问题是：按官方 loader 参数装入文件后，OpenSBI 的下一阶段地址为 `0x0`。这发生在进入内核之前，与内核开启分页后的故障属于不同层次，分别处理。

## 六、实验总结与收获

### 6.1 实验知识点与 OS 原理的联系

| 实验知识点 | 对应 OS 原理 | 含义、联系与差异 |
|------------|-------------|------------------|
| Trap frame 保存与恢复 | 执行上下文保护 | 用确定布局保存被打断程序的状态；本实验保存当前整数上下文，不等同于完整进程控制块 |
| 硬件 CSR 与软件通用寄存器保存 | 中断入口中的软硬件分工 | 硬件记录原因和返回信息，软件补齐通用寄存器；仅有硬件入口不能保证 C 处理后状态不丢失 |
| 汇编入口调用 C 函数 | ABI 与内核接口 | 通过参数寄存器和栈约定连接不同语言；普通函数调用只需遵守 ABI 的保存责任，Trap 返回还要恢复被异步打断的寄存器 |
| `sepc` 与 `sret` | 异常返回和特权级恢复 | 处理函数决定合法返回位置，恢复代码落实该状态，处理器完成特权返回；其机制不同于普通 `ret` |
| 最后恢复 `sp` | 栈管理与上下文一致性 | 保存帧既是数据也是恢复期间的寻址依据，提前改变基址会破坏剩余加载 |
| `scause` 标志与原因分离 | 中断与异常的分类分发 | 中断由异步事件引起，异常与当前指令有关；分发后仍保留原始原因用于诊断 |
| `clock_set_next_event()` 与 `ticks` | 时钟管理与抢占的基础 | 本实验安排下一事件并统计次数；时钟中断本身不等于进程调度，也未发生运行进程切换 |
| `SIE`、`STIE` 和本地中断保存恢复 | 中断屏蔽与临界区 | 使能条件和状态恢复共同保证单 hart 下的操作边界；不能代替多核锁或内存屏障 |
| 16/32 位 EPC 推进 | 同步异常的恢复策略 | 返回地址必须落在下一条指令边界；本实验选择跳过，不代表真实 OS 对所有非法指令都这样处理 |
| 启动恒等映射与高地址映射 | 虚拟内存与引导 | 开启地址翻译后仍需覆盖过渡取指；相同物理页可有多个虚拟别名，页表覆盖不等于可分配内存 |
| SBI 时钟与关机接口 | 特权层次与固件服务 | S 模式内核通过约定接口请求固件服务；本实验未实现 M 模式定时器及平台关机驱动 |

从 Lab2 到 Lab3，内存管理不再只是顺序执行的一组函数。中断可能在内核执行途中到来，保存现场、恢复使能状态和保护共享数据都成为正确性条件。Trap frame 记录的是一次进入内核的执行现场；完整进程切换还需要进程状态、地址空间和调度策略，两者不能等同。

### 6.2 AI 协作开发的经验

**先提供真实接口，再要求实现。** 模块一把 `SAVE_ALL`、结构体和 ABI 写入依赖条件；模块二明确 `cause` 仍带标志、EPC 使用内核虚拟地址、时钟阈值按输出次数计算。这样的 Spec 能约束状态变化，减少 AI 自行假设布局、固定加 4 或错误转换地址的机会。

**把实现、启动和专项验证分轮。** 内存前置迁移、两个处理函数、启动页表和边界测试分别限定修改范围。对象编译通过时没有宣称完整内核可运行；隔离副本启动时也没有宣称正式源码已修复。每轮以实际 diff、构建和日志决定下一步，避免一次扩大修改范围掩盖故障来源。

**用可以区分错误实现的用例验收。** 只有普通编号和压缩断点不足以验证完整行为。大于 32 位的原因能暴露整数截断，2 mod 4 的四字节指令能检查长度与访问方式，连续 1000 次时钟能区分“评分在 200 次通过”和“关机边界正确”。测试接口、状态不变量和成功条件应在提示词中说清楚。

**同时审查测试与工具环境。** CRLF 计数、短缓冲诊断、仓库定位和 QEMU 退出码都曾影响判断。失败时先看原始日志，判断问题属于正式实现、测试预期还是加载环境，再修改对应位置。不能因为日志有成功字符串就跳过失败检查，也不能因为测试使用了替身就声称真实硬件路径通过。

**保留历史与人工决策。** 代码迁移读取指定 Git 版本，不整文件覆盖队友成果；失败证据、修复差异和源码指纹一起保留。提示词说明了工作边界，提交由成员逐次确认。AI 给出的完成说明仍需结合仓库、源码和证据核对。

### 6.3 OS 原理中重要但本实验未对应实现的内容

| 原理内容 | 与本实验的关系及未实现部分 |
|----------|--------------------------|
| 进程、线程与调度 | 时钟中断提供调度时机，但当前仅计数和输出，没有任务队列、时间片分配或进程切换 |
| 用户态隔离与系统调用 | 当前运行在 S 模式，未建立用户地址空间、用户 Trap 栈切换、系统调用表或参数检查 |
| 按需分页与缺页恢复 | 启动页表保证映射可达；本次不实现分配缺页、页替换、交换或写时复制 |
| 多核同步与内存一致性 | 本地关中断只影响当前 hart；多核共享页管理器仍需锁、原子操作和相应内存顺序 |
| 外设驱动与中断控制器 | 分类提示不等于驱动；未实现 PLIC 的领取/完成、设备状态清除或中断下半部 |
| 文件系统与持久化 I/O | 实验没有文件、块设备缓存、日志恢复或权限管理机制 |
| 信号与故障隔离 | 真实 OS 可终止故障任务或向进程递送信号；本实验仅诊断并对两类异常跳过指令 |

本实验完成了“进入 Trap—保存现场—分类处理—恢复现场—返回”的基础流程。更完整的操作系统会在这个入口上衔接调度、地址空间、设备管理与故障隔离，而不只输出提示。
